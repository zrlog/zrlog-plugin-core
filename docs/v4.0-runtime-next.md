# 插件运行时约束与验证

本页维护已实现的运行时边界。包结构见[架构说明](plugin-core-architecture.md)，
HTTP 接口见 [OpenAPI](api/openapi.yaml)，前后端文案见 [i18n 说明](i18n.md)。

## 能力注册与调用

- 插件业务代码运行在独立进程，依赖 `zrlog-plugin-common`。`NioClient` 在插件侧读取
  `@Service`、`@Capability`、`@ScheduledCapability`，通过 `INIT_CONNECT` 上报元数据；core 不扫描插件 classpath。
- 能力由 `pluginId + capabilityKey` 定位。`CapabilityRegistrationService` 校验注册信息，
  不根据 capability key 猜测缺失的 `serviceName`；旧 `ActionType.SERVICE` 路径继续兼容。
- 调度、通知和内部 capability 调用使用 `RuntimeCapabilityInvokerFactory` 创建的完整调用链。
  `TrackingCapabilityInvoker` 校验能力存在、enabled、exposure 和风险策略，再按需启动插件、
  记录调用开始、调用 Socket、记录完成与 invocation log。`SocketCapabilityInvoker` 只负责传输。
- `CapabilityRiskPolicy` 支持 low / medium / high / critical；不支持的值拒绝注册，
  high / critical 能力不允许 MCP exposure，历史持久化数据也在调用边界校验。
- 运行态生命周期只表示进程、连接和路由状态；调度、通知和业务能力的失败保留在各自结果中。
- 生产环境未登录访问非公开插件路径返回 403；`DEV_MODE` 请求头不能绕过鉴权。

## 调度与运行态

- `InternalSchedulerRunner` 在非 FaaS 模式下启动时检查一次，此后按整分钟扫描。
  只领取 enabled 且到期的任务；普通 tick 不等同于单条任务的“立即执行”。
- 系统运行态维护默认每 300 秒执行，间隔来自 `PluginRuntimeSetting.idleScanIntervalSeconds`。
  维护包含状态清理和按设置执行的空闲回收，具体逻辑由 `RuntimeSystemAutomations` 与 `SchedulerRuntime` 维护。
- FaaS 模式跳过内部定时器，可由外部调度器调用 tick。
  对外路径为 `/api/plugin/open/scheduler/tick`，core 实际路由为 `/open/scheduler/tick`；
  完整 URL 使用页面生成的地址，路径定义集中在 `SchedulerExternalEndpoint`。
  外部请求通过 `Authorization: Bearer <secret>` 校验启用的 provider。
- 管理页使用 `/api/runtime-scheduler/tick`；单条立即执行使用 `/api/runtime-automations/run`。
  管理路由的别名、鉴权和代理边界以 `PluginHttpServerConfig` 及其测试为准。
- 调度设置由调度中心管理。插件通过 `SCHEDULER_QUERY` 查询自身任务；
  `SCHEDULER_UPDATE` 及其 request/result 模型保留兼容，但写请求一律返回失败。
- 并发领取使用进程内互斥、数据库锁和任务租约；KV 更新使用版本比较。
  调整锁、超时或回收时须验证多实例竞争以及正在执行的调用，不能把完成响应替换为仅已提交。

## 通知与系统事件

- `NotificationRuntime` 按逻辑渠道选择 provider，经统一能力调用链投递并保存 delivery log。
  core 不管理 SMTP、邮件模板、提醒任务等插件业务配置。
- 管理页可通过 `/api/runtime-notification/test` 测试指定 provider；该接口不代替插件的
  `NOTIFICATION_PUBLISH` Socket 调用。最近投递状态来自实际执行结果。
- reminder 按 `plugin.reminder.notification.channels` 选择渠道，未配置时兼容默认 email；
  旧 `emailNotify` 表示是否允许通知。通知未成功不能标记已提醒。
- 系统事件由 `RuntimeEventRuntime` 与 `RuntimeEventHandlerResolver` 处理。
  `type=event_handler`、`exposure=runtime_event`，当前使用 `channel` 声明订阅事件，可逗号分隔。
  `system.refreshCache` 兼容 `refresh_cache` / `REFRESH_CACHE`；没有 handler 的已运行旧插件
  继续接收 `ActionType.REFRESH_CACHE`，旧广播不负责启动插件。
- MCP 协议、Quartz adapter 和独立 audit/security 策略体系不属于当前运行时能力。

## 存储

运行时继续使用 `website` KV，不新增业务表；业务插件维护自己的配置，core 不直接读写插件私有业务结构。

| 数据 | key | 保留限制 |
| --- | --- | --- |
| 核心配置 | `plugin_core_db_key` | `PluginCore` 模型 |
| 能力注册 | `plugin.runtime.capabilities` | `CapabilityStore` |
| 调度任务 | `plugin.runtime.automations.v2` | `AutomationStore` |
| 调度记录 | `plugin.runtime.automationRuns.v2` | 最近 500 条 |
| 插件状态 | `plugin.runtime.states` | 实例清理策略 |
| 通知投递 | `plugin.runtime.notificationDeliveries.v2` | 最近 500 条 |
| 调用日志 | `plugin.runtime.invocationLogs.v2` | 最近 1000 条 |

各 Store 使用具体 document 类型和 Gson class，保留 schema、version、updatedAt 等字段，
避免以匿名泛型承载 Native 序列化契约。JSON 大小限制集中在 `PersistentJsonLimits`，
错误文本限制由 `RuntimeTextLimits` 处理。

`WebsiteRuntimeKvStore.get()` 每次查询数据库；其 snapshots 保存用于条件更新的版本信息，
不是读取缓存。`remark` 中的版本标记参与 CAS，不能通过删掉读取或锁操作来简化并发语义。

## 验证入口

后端修改在工程根目录运行：

```sh
./mvnw test
```

专项测试入口：

| 改动范围 | 现有测试 |
| --- | --- |
| 调用校验与状态跟踪 | `TrackingCapabilityInvokerTest` |
| 调度、查询与废弃写入口 | `SchedulerRuntimeTest`、`SchedulerQueryServiceTest`、`SchedulerUpdateServiceTest` |
| 定时器与外部路径 | `InternalSchedulerRunnerTest`、`SchedulerExternalEndpointTest`、`BearerSchedulerAuthTest` |
| 通知与事件 | `NotificationRuntimeTest`、`RuntimeEventRuntimeTest` |
| KV 并发与日志限制 | `WebsiteRuntimeKvStoreTest`、`PluginRuntimeStateStoreTest`、`InvocationLogStoreTest`、`NotificationDeliveryStoreTest` |
| 路由与初始化 | `PluginHttpServerConfigTest`、`ServerActionHandlerInitConnectTest` |
| Native warmup | `GraalvmAgentApplicationTest` |

Native 改动须检查 `GraalvmAgentApplication`、`NativeRuntimeWarmup`、common 的
`PluginNativeImageUtils` 以及实际反射/资源配置，覆盖 DTO、枚举和注解读取。
JVM 测试和 agent 采样不能替代实际 Native 构建与运行验证。

跨插件变更还需验证：未启动 provider 的按需拉起、提醒到期扫描、通知成功/失败、
调用记录和投递记录、调用完成后的空闲回收。前端验证命令见[前端说明](../src/main/frontend/README.md)。
